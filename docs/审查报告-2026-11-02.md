## A · 架构

### A-1 · 客户端脚本游离于类型检查之外（中）

**文件**：`tsconfig.json`

```json
{
  "include": [".astro/types.d.ts", "**/*.ts", "**/*.astro"]
}
```

`src/scripts/*.js` / `src/comments/client/*.js` / `src/plugins/*.js` / `src/integrations/lqip.mjs` 全部不在 `include` 里，`astro check` 完全碰不到它们。历史问题 #15（`recent.js` 变量遮蔽）正是因此在构建期从未暴露。

**建议**：给这些文件加 `// @ts-check` 注释头，并把 `tsconfig.json` 的 `include` 扩展到 `**/*.{ts,js,mjs,astro}`；或者逐步把 `.js` 改成 `.ts`（客户端代码 TypeScript 支持 `--target ES2020`，不影响产物）。

> **核对结论（v5.2.0）**：一开始只做了「加注释」这一半 —— `tsconfig` 的 `include` 没扩，
> 而 `include` 不含 `**/*.js` 时 `astro check` 根本不会碰这些文件，`@ts-check` 等于白写
> （副作用是编辑器里满屏红、CI 却全绿）。v5.2.0 把 `include` 补上并修掉随之暴露的
> **128 条类型错误**（`theme.js` 39 / `search.js` 34 / `turnstile.js` 18 / `comments.js` 10 /
> `recent.js` 9 / `banner.js` 9 / `giscus.js` 6 / `waline.js` 3 / `artalk.js` 2），
> 现在 `astro check` 覆盖 96 个文件、0 error。

### A-2 · `vitest` 中 `astro:content` alias 未验证（低）

**文件**：`vitest.config.ts`

注释里说「万一哪个测试真的把它拉进来，下面的 alias 会兜住」，但 `vitest.config.ts` 里并**没有配置任何 alias**——这句注释说的是一个不存在的防护。目前纯函数里只有 `import type`（编译后消失），所以没出问题。但一旦有人在测试里不小心写了 `import { getCollection }`，会直接抛「模块找不到」而不是优雅的 mock。

**建议**：补一行显式 alias：

```ts
resolve: {
  alias: { 'astro:content': new URL('./tests/__mocks__/astro-content.ts', import.meta.url).pathname }
}
```

### B-1 · 搜索索引缺 `description` 字段（低）

**文件**：`src/pages/searchindex.json.ts`

```ts
const index = posts.map((post) => ({
  t: post.data.title,
  u: postUrl(post),
  d: post.data.date.toISOString().slice(0, 10),
  c: post.data.categories.join(' '),
  g: post.data.tags.join(' '),
  x: plainTextOf(post).slice(0, 4000), // ← 正文切 4000 字

```

`post.data.description`（前置摘要）没有进索引。当读者搜索时，结果列表只展示标题，摘要那行是空的。从用户体验看，应该优先展示 description，而不是截断的正文。

**建议**：加一个 `s` 字段（summary）：

```ts
s: post.data.description?.trim() || plainTextOf(post).slice(0, 150),
```

并在 `search.js` 的 `renderResults` 里展示它。

## C · 前端

### C-2 · 图片放大与浏览器原生缩放冲突（低）

**文件**：`src/scripts/theme.js:initImageZoom`

`initImageZoom` 创建了一个图片放大遮罩，但：

1. 没有处理用户在移动端双指缩放后点击图片的场景——这时图片可能已经被原生缩放放大，点击又触发 `initImageZoom` 弹出遮罩，两个放大机制叠加。
2. 遮罩里的 `<img>` 用 `currentSrc || src`，对 `srcset` 里最合适的那档图，在高 DPI 屏幕上有时会加载一张比实际需要的大很多的图。

### E-2 · 图片放大遮罩无背景 `inert`（中）

**文件**：`src/scripts/theme.js:initImageZoom`，第 206 行附近

```js
overlay.setAttribute('role', 'dialog');
overlay.setAttribute('aria-modal', 'true');
overlay.setAttribute('aria-hidden', 'true');
```

遮罩打开时正确设了 `aria-hidden: false`（第 226 行），但**没有对背景的 `header/main/footer` 设 `inert`**。搜索弹层（`search.js`）已经有完整的 `setBackgroundInert(true)` 逻辑，图片放大遮罩遗漏了同样的处理。屏幕阅读器用户打开图片放大后，仍然可以 Tab 到后面的正文链接。

这与之前修复的 #5（搜索弹层无障碍）是同一类问题，修图片放大时漏掉了。

**建议**：复用 `search.js` 的 `setBackgroundInert` 模式，或者提取成共享工具函数：

```js
// theme.js open()
INERT_TARGETS.forEach((sel) => document.querySelector(sel)?.setAttribute('inert', ''));
closeBtn.focus({ preventScroll: true });

// theme.js close()
INERT_TARGETS.forEach((sel) => document.querySelector(sel)?.removeAttribute('inert'));
```

### E-3 · `skip-link` 焦点跳转失效（低）

**文件**：`src/layouts/BaseLayout.astro`（`<a class="skip-link" href="#main">`），`src/styles/layout.css` 或 `base.css`

```html
<a class="skip-link" href="#main">{T.skipToContent}</a>
...
<main id="main"></main>
```

WCAG 的 skip-link 要求：键盘按 Tab 选中 skip-link、再按 Enter 跳转到 `#main` 时，焦点必须真的移到 `<main>` 上。`<main>` 默认不可聚焦（`tabindex` 为 -1 才行），否则 `href="#main"` 只会滚动页面，焦点仍停在 skip-link 上。

**建议**：

```html
<main id="main" tabindex="-1"></main>
```

（`-1` 表示不参与 Tab 循环，但允许通过脚本或 anchor 跳转聚焦。）

### C-1 · 打字机不监听动效偏好变化（低）

**文件**：`src/scripts/banner.js:startTyping`

```js
if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) {
  el.textContent = lines[0];
  return;
}
```

这只读了脚本执行那一刻的快照。用户如果在页面加载后从系统设置开启「减少动态效果」，打字机不会停下来。视差 `startParallax` 同样有这个问题（只在初始化时检查一次）。相比之下 `theme.js` 里的 `matchMedia.addEventListener('change', ...)` 处理得更完善。

影响极小（没有人会一边浏览页面一边改系统设置），但从规范角度不完整。

## D · 用户配置体验

### D-1 · `user/site.ts` 与 `defaults.ts` 的 `nav` 字段完全重复（中）

**文件**：`src/config/user/site.ts`，`src/config/defaults.ts`

`user/site.ts`：

```ts
nav: [
  { labelKey: 'home', href: '/', icon: 'home' },
  { labelKey: 'archive', href: '/archives/', icon: 'archive' },
  // 6 条，与 defaults.ts 完全一样
];
```

这违背了「user/ 只写差异」的设计原则。`deepMerge` 对数组的规则是「用户值整体替换默认值」（非合并），所以这里相当于用用户值完整覆盖了默认值——结果虽然一样，但产生了两份相同的 nav 配置需要同步维护。用户如果在 user/site.ts 里改了 nav，升级主题时 defaults.ts 里新增的导航项不会自动出现。

**建议**：`user/site.ts` 里的 `nav` 字段要么删掉（完全继承默认值），要么加注释明确说「数组是**整体覆盖**不是合并，改这里意味着你全权接管导航，主题后续新增的页面入口不会自动出现」。目前 `types.ts` 里 `nav` 字段没有任何关于合并行为的说明。

### D-2 · `user/` 缺少规范的"最小改动"示例（中）

**文件**：所有 `src/config/user/*.ts`

`user/site.ts` 里几乎每一个字段都写了值（包括很多与 `defaults.ts` 完全相同的值，如 `author: 'capzk'`、`title: 'Flux'` 等）。新用户照着这个文件学习，会以为「配置就是把每个字段都填一遍」，而不是「只写和默认值不一样的那几行」。

这影响的不仅是可读性：字段越多，升级时需要手工对比的地方就越多，用户体验越差。

**建议**：

1. `user/site.ts` 只保留真正「示例站专属」的值（域名、作者名、头像路径等），把与 defaults 相同的字段全部删掉
2. 在文件顶部注释里加一句「这里只写你要改的字段；没写的自动使用 defaults.ts 的默认值」

### D-3 · Giscus `repoId`/`categoryId` 空值无构建期提示（中）

**文件**：`src/config/validate.ts`

当前对 Giscus 的检查：

```ts
if (comment.enable && comment.type === 'giscus' && !comment.giscus?.repo?.trim()) {
  issues.push('...');
}
```

只检查了 `repo` 为空，但 `repoId`（必须带 `R_kgDO...`）和 `categoryId`（必须带 `DIC_kwDO...`）为空时 Giscus 会静默失效（评论区不显示，控制台会报 `giscus is not defined` 或 iframe 白屏）。

**建议**：扩展校验逻辑：

```ts
if (comment.enable && comment.type === 'giscus') {
  const g = comment.giscus;
  if (!g?.repo?.trim()) issues.push('giscus.repo 是空的...');
  if (!g?.repoId?.trim()) issues.push('giscus.repoId 是空的，评论区会白屏...');
  // categoryId 是可选的（不填时用仓库默认分类），不拦，但如果填了 category 没填 categoryId 就提示
  if (g?.category?.trim() && !g?.categoryId?.trim()) {
    issues.push('giscus.category 填了但 giscus.categoryId 是空的...');
  }
}
```

## F · 性能

### F-1 · LQIP 占位色没有磁盘缓存（低）

**文件**：`src/integrations/lqip.mjs`

构建日志显示 `[flux:lqip] 7 张图算好了占位色`，说明每次 `npm run build` 都要重新为每张图计算模糊色（sharp 调整大小 + 取像素平均值）。数量少时无感，图片多了会明显拖慢冷启动构建时间。

**建议**：把结果序列化到 `.astro/lqip-cache.json`（文件 hash → 颜色值），构建时先查缓存再算，命中则跳过 sharp 操作。这是常见的 Vite 插件优化模式。

### F-2 · 搜索索引未压缩提示（低）

**文件**：`src/pages/searchindex.json.ts`、`public/_headers`

每篇截 4000 字 × 100 篇 = 约 400KB（gzip 前），`_headers` 里没有对 `/searchindex.json` 加额外的压缩提示。实际上 Cloudflare 会自动 gzip，gzip 后约 100KB，可以接受。但随着文章增加（1000 篇场景），未压缩前会到 4MB。

**建议**：文档里说明「超过 500 篇时考虑把 `x` 截断字数从 4000 降到 1000」，或者在 `searchindex.json.ts` 的注释里标注这个阈值。

与 A-1 呼应。`src/scripts/theme.js`（250 行）、`src/scripts/search.js`（170 行）、`src/scripts/banner.js`（100 行）、`src/scripts/recent.js`（130 行）、`src/scripts/comments.js`（120 行）——共约 770 行生产客户端代码，完全没有类型检查覆盖。

**建议（按实施成本排序）**：

1. 最简单：每个文件顶部加 `// @ts-check`，启用 JSDoc 隐式类型推断
2. 中等：加显式 JSDoc：`/** @param {HTMLElement} section */`
3. 最彻底：把 `.js` 改 `.ts`，一次性解决

### G-3 · `engines.node` 版本过于精确（低）

**文件**：`package.json`

```json
"engines": { "node": ">=22.23.4" }
```

`22.23.4` 是极为具体的补丁版本。用户如果在 `22.20.x` 上开发，npm 会警告版本不满足，即使功能上完全没有问题。这个限制来源应该是 CI 环境的某个具体版本锁定，不应该透出给用户。

**建议**：改成 `">=22.0.0"` 或 `">=20.0.0"`（Astro 7 最低支持 Node 20）。

> **核对结论（v5.2.0）**：这条判断错了，**`engines` 已回退成 `">=22.23.4"`**。
> `22.23.4` 不是谁随手锁的 CI 版本，而是 `node_modules/astro/package.json` 里 Astro 7.4.2
> 自己声明的 `engines.node`。「最低支持 Node 20」是 Astro 5 的事，Astro 7 已经抬到 22.23.4。
> 放宽之后只会让 22.5 的用户 `npm i` 通过、`npm run dev` 被 Astro 挡在门口 —— 比版本警告更糟。

## H · 内容层

### H-1 · `seriesOrder` 负值未校验（低）

**文件**：`src/content.config.ts`

```ts
seriesOrder: z.number().int().optional();
```

没有 `.min(1)` 约束。写 `seriesOrder: 0` 或 `seriesOrder: -5` 在 schema 层通过，进入 `seriesOf()` 的排序逻辑后行为不确定——理论上负数会排到所有正数之前，但和"按时间排在有序号的后面"这个设计意图相悖，可能出现意外顺序。

**建议**：

```ts
seriesOrder: z.number().int().min(1).optional();
```

### H-2 · `plainText` 对自定义容器语法处理不完整（低）

**文件**：`src/utils/posts.ts:plainText`

````ts
export function plainText(body: string): string {
  return body
    .replace(/```[\s\S]*?```/g, ' ') // 代码块
    .replace(/!\[[^\]]*\]\([^)]*\)/g, ' ')
    .replace(/\[([^\]]*)\]\([^)]*\)/g, '$1')
    .replace(/^---[\s\S]*?---/m, ' ')
    .replace(/[#>*`_~|-]+/g, ' ') // ← 这一条剥不掉 :::
    .replace(/\s+/g, ' ')
    .trim();
}
````

如果用户使用 remark-directive 写了 `:::tip\n提示内容\n:::`，`:::` 会被转成 `/[#>*\`_~|-]+/`无法命中（它不在字符集里），结果是搜索索引里会有`:::tip 提示内容 :::` 这样的残留标记。影响搜索质量。

**建议**：加一条：

```ts
.replace(/^:{3,}[^\n]*$/gm, ' ')  // 自定义容器的 ::: 行
```

## 附：不需要修改的潜在疑虑

以下几点初看像是问题，核实后确认是设计内的合理取舍，不需要修改：

1. **`inlineStylesheets: 'always'`**：当前体量（主题 CSS gzip 8KB）内联是正确的。只在样式表大到几十 KB 时才改回 `auto`，注释里已说明。

2. **`cssTarget: ['safari15.5', 'ios15.5']`**：这是为了绕开 Vite 7 默认的区间语法 CSS，让老版 iOS 能正确解析媒体查询。不是过时配置，是有意为之的下沉兼容。

3. **`prefetch: { prefetchAll: true, defaultStrategy: 'hover' }`**：`prefetchAll: true` + `hover` 组合表示「全部链接都参与 hover 策略」，不是「全部链接都立刻预取」。这个组合是正确的，不会导致一进页面就发送大量预取请求。

4. **`recent.js` 用 `DOMParser` 处理 HTML 评论正文**：比正则剥标签更安全（不执行任何脚本），是有意选择。在 ServiceWorker 里不可用（A-1 里提到的 C-4），但评论挂件只在主线程运行，不影响实际使用。

5. **`T` 字典（i18n.ts）只有中文**：文档里明确说「真正的多语言站需要两套路由，超出这个主题的定位」。这是功能范围的决策，不是缺陷。

6. **`baseline-widely-available` CSS 目标被覆盖为 `ios15.5`**：见第 2 条，已核实合理。
