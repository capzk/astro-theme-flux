# Flux · 静态页面加载与线上访问性能审查

- 审查日期：2026-11-02
- 审查对象：`astro-theme-flux` v5.2.0（示例站 `astro-theme-flux.pages.dev`）＋ 生产站 `www.capzk.com`
- 审查范围：构建产物、关键渲染路径、缓存与传输、资源体积、图片与脚本策略、可扩展性
- 审查方式：产物度量（`dist/` 逐文件统计）＋ 线上响应头实测（`curl -D -`）＋ 源码走查
- 不在范围：服务端渲染耗时（本项目为纯静态）、Waline 服务端、CDN 计费

---

## 一、结论摘要

这个主题的性能底子是**扎实的**：零外链阻塞资源、系统字体栈、hashed 资源长缓存、Brotli 与 HTTP/3 均已生效、评论与分析全部按需加载。首访关键路径已经接近静态站的理论下限。

真正的问题不在"资源多大"，而在**缓存层**：HTML 响应既没有验证器（ETag / Last-Modified），又被标成 `max-age=0, must-revalidate`，于是**每次回访都必须重新下载整份 HTML，而不是一个 304**。这是当前唯一一处"用户能明确感觉到"的损失，也是最容易修的一处。

| 维度             | 评级  | 依据                                                                  |
| ---------------- | ----- | --------------------------------------------------------------------- |
| 关键渲染路径     | A     | 无外链 CSS / 无字体请求 / 无同步脚本 / 无第三方阻塞                   |
| 缓存与验证器     | **C** | HTML 无 ETag、`must-revalidate`、`cf-cache-status: DYNAMIC`           |
| 资源体积         | B+    | 首页 20.2KB(gzip)；但 46KB CSS 全站内联、页面级未拆分                 |
| 图片策略         | B     | srcset / sizes / lazy / width-height 齐全；档位上限偏低               |
| JS 策略          | B+    | 8.6KB 单包 + 模块化 defer；文章页专属逻辑在列表页也下载               |
| 第三方与延迟加载 | A-    | analytics async、Waline 滚动 600px 才加载、搜索索引 pointerenter 预取 |
| 协议与传输       | A-    | Brotli 实测生效、HTTP/3 可用（alt-svc）、immutable 长缓存正确         |

**优先级排序**：P0 缓存验证器（一行头改动，回访收益最大）→ P1 LCP 预加载与 301 缓存 → P2 CSS/JS 按页拆分 → P3 索引瘦身。

## 三、问题清单

### P0-1　HTML 缺验证器 + `must-revalidate`：回访全量重传

**证据**

- 响应头只有 `Cache-Control: public, max-age=0, must-revalidate`，没有 `ETag`，也没有 `Last-Modified`。
- 带 `If-None-Match` 请求仍返回 `200`（因为服务端根本没有校验器可比对）。
- `cf-cache-status: DYNAMIC`：边缘节点不缓存 HTML，每次都回到 Pages 的源。

**机理**

`max-age=0` 让副本立即过期，`must-revalidate` 要求"过期后必须先验证才能复用"。而验证需要验证器：有 ETag 时服务端回 `304`（约 200 字节），没有就只能回完整 `200`（20KB）。两条合起来，站内每跳一次都重新下一份完整文档。

**影响**

回访场景（P75 会话 2–4 页）：多传 40–80KB、多 2–4 次完整文档往返。移动网络下这是可感知的。

**方案**

`public/_headers` 里 `/*` 那条改成：

```
/*
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  ! Cache-Control
  Cache-Control: public, max-age=0, s-maxage=3600, stale-while-revalidate=86400
```

- `s-maxage=3600`：让 Cloudflare 边缘缓存 HTML（目标是把 `DYNAMIC` 变成 `HIT`），回访在边缘终结。
- `stale-while-revalidate=86400`：浏览器允许先用手上的旧副本、后台再更新 —— 这一句正好绕开"没有 ETag 就只能全量重下"的死结。
- Pages 每次部署会清边缘缓存，1 小时的 s-maxage 不会让新文章延迟可见。

若 `_headers` 不生效（见下），等价做法是在 CF 后台加一条 Cache Rule：`http.host eq "www.capzk.com"` → Eligible for cache + Edge TTL 1h + Browser TTL "respect origin"。

**必须实测**

改完用两次同一 URL 的 `curl -D -` 看 `cf-cache-status` 是否从 `DYNAMIC` 变 `HIT`、是否出现 `age:`。**不要假设写了就一定生效。**

**风险**

生产站已经观察到 CF 后台有规则覆盖了主题的 `_headers`：主题写的是 `referrer-policy: strict-origin-when-cross-origin`，线上实际是 `referrer-policy: same-origin`。说明存在 Transform Rules（或 Pages 项目设置），可能同时改写了 `Cache-Control`。落地前先在 CF 后台确认没有规则盖掉这条。

### P1-1　banner 走 `<Image>` 时没有 `preload`，LCP 晚一拍

**证据**

`src/components/Banner.astro` 里 `<Image loading="eager" fetchpriority="high">`，没有 `priority`。
`BaseLayout.astro` 的 `<link rel="preload" as="image">` 只在 banner 是**字符串路径**时输出（注释里明确写了"import 进来的资源由 `<Image>` 输出 `fetchpriority="high"`，不用管"）。

**机理**

`fetchpriority="high"` 只调整"已发起请求"的优先级，不能让资源**更早被发现**。预加载扫描器（preload scanner）在解析 `<head>` 时就工作，但 `<img>` 在 `<body>` 里、且被 `.banner-bg` 包着，要等主解析器推进到那里才知道要下载。`<link rel="preload" as="image" imagesrcset=... imagesizes=...>` 才能把它提到扫描阶段。

生产站首页 banner 用的正是 `import bannerImg`（3840×2160 原图 → 四档 webp），属于这条的命中场景。

**方案（已落地，实测修正）**

原判断「加 `priority` 就会输出 preload」**是错的**。查
`node_modules/astro/dist/assets/internal.js:113` 可见，Astro 7 的 `priority` 只做三件事：
`loading ??= 'eager'`、`decoding ??= 'sync'`、`fetchpriority ??= 'high'`，然后把 `priority`
删掉。它不碰 `<head>`。

正确做法是在 `BaseLayout` 的 frontmatter 里自己算：

```ts
const bannerAssetPreload =
  bannerSource && isAsset(bannerSource)
    ? await getImage({ src: bannerSource, widths: BANNER_WIDTHS, sizes: BANNER_SIZES })
    : null;
```

head 里输出 `href={bannerAssetPreload.src}` + `imagesrcset={bannerAssetPreload.srcSet.attribute}`

- `imagesizes`。**参数必须与 `<Banner>` 的 `<Image>` 完全一致**（同一组 widths/sizes、都不传
  format），Astro 才会命中同一份产物；否则会「预加载一张、实际又下一张」，比不预加载更糟。
  档位常量放在 `utils/image.ts`（`BANNER_WIDTHS` / `BANNER_SIZES`），两处共用。

用临时探针页验证过：preload 的 `href` / `imagesrcset` 与 `<img>` 的 `src` / `srcset`
逐字节一致，验证后探针已删除。

**预期**：LCP 提前一个"解析到 body"的阶段，慢设备上约 30–80ms。

### P1-2　apex → www 的 301 没有缓存

**证据**：`curl -sI https://capzk.com/` 返回 `301`，只有 `Location` 与 HSTS，无 `Cache-Control`。

**影响**：从 apex 进入的每一次（外链、搜索结果的旧链接、分享）都要多一个往返才落到真实页面。

**方案**：CF 后台 Redirect Rule / Bulk Redirects 里给该 301 加 `Cache-Control: public, max-age=86400`。长期做法是确定唯一主域（HSTS preload 已经开了，适合彻底单域）。

### P2-1　CSS 全站内联，页面级未拆分

**证据**

- 每页内联 40–46KB（minified），首页与归档页只差 5.6KB。
- `post.css`(13.7KB) + `post-footer.css`(7.4KB) + `comments.css`(7.0KB) + `code.css`(4.3KB) + `terms.css`(4.4KB) ≈ **36.9KB 源码**，在首页 / 归档 / 标签页完全用不到。
- `main.css` 一条 `@import` 串起 13 个分片，所有页面共用同一份产物。

**评价**

`inlineStylesheets: 'always'` 的取舍本身是对的（省一个 RTT，体量小时划算），配置里的论证站得住。问题只在于**一份 CSS 服务所有页面**：列表页背着文章页的排版规则。

**方案**

`src/styles/main.css` 拆成两层：

- `base.css`：tokens / base / layout / cards / footer / overlays / responsive（全站，继续内联）
- `post.css`：post / code / post-footer / comments（只在文章页 `import`）
- `terms.css`：只在标签、分类、归档页 `import`

思路是"页面 import 不同的入口"，让 Astro 为每类页面生成不同的内联块。**不要**顺手改成外链 CSS——那会把首访的 0 RTT 优势还回去。

**预期**：列表页内联 CSS 从 46KB 降到约 28KB（br 后 -3～4KB）。
**风险**：拆层最容易漏 `@import` 顺序（CSS 规范要求 `@import` 在规则之前），且页面级样式缺失只会在特定模板暴露。需要 `npm run check` + build + 逐类页面对比回归。

### P2-2　`theme.js` 单包，文章页专属逻辑在列表页也下载

**证据**

`BaseLayout.astro` 底部静态 `import '../scripts/theme.js'`，产出单 chunk 8.6KB。其中：

- `initToc`（目录高亮）：只有文章页有 `.toc-link`
- `initImageZoom`（正文图片放大）：只有 `.markdown-body`
- `initCodeCopy`：只有 `.code-copy`

三者都是"查不到 DOM 就 return"，逻辑正确、但字节照付。

**方案**

复用 `search.js` 已有的模式：

```js
if (document.querySelector('.toc-link, .code-copy, .markdown-body img')) {
  void import('../scripts/post-widgets.js');
}
```

把 TOC / 代码复制 / 图片放大挪进去。首页、归档、标签、分类页省下这部分。

**预期**：列表类页面 -3.5KB raw（br 后约 -1.3KB），少一次 parse/compile。文章页会多一个 chunk 请求，但 HTTP/2 多路复用下代价很小，且可被 prefetch 掩盖。
**判断**：收益偏小，属于"顺手做"级别；如果拆分会显著增加维护成本，可以不做。

### P2-3　卡片图档位上限 560w，移动端实际不足

**证据**

`PostCard.astro`：`widths={[240, 400, 560]}`、`sizes="(max-width: 767px) 100vw, 240px"`。
`responsive.css` 里 `.index-img { width: 100% }`，窄屏卡片封面确实是满宽。

**机理**

375 CSS px 视口 × DPR 3 = 1125 物理像素，而最大候选只有 560w，等于放大 2×。桌面端 `240px` 对应 240w 档，是正确的。

**方案**：补一档 800w（或把 `sizes` 改成 `calc(100vw - 2rem)` 让选择更精确）。banner 的 720/1080/1440/1920 在 4K@2x 下同理偏小，但氛围图可接受，优先级更低。

**收益**：画质而非速度。移动端封面尺寸会从 ~6KB 涨到 ~10KB，需权衡。

### P3-1　搜索索引可瘦身

**现状**：84.7KB raw / 37.3KB gzip（57 篇），字段 `x` 存正文前几百字，是体积大头。`pointerenter` 就预取，这个时机是对的（早于点开）。

**评估**：57 篇规模下 37KB 完全可接受。但这是**线性增长**的：300 篇会到 150KB+，届时移动端首次搜索会明显卡。

**方案（等到规模上来再做）**：`x` 截到 160 字；或按分片（首页 N 篇先加载，其余按需）。现在不动。

### P3-2　HTML 里的中文注释（930 B，占 0.9%）

`BaseLayout.astro` 的 HTML 注释被原样输出。剥掉能省 0.9KB（br 后约 0.3KB）。**不建议动**——注释对二次开发和 fork 的人有价值，收益与成本不成比例。

## 四、明确不建议做的

| 想法                                         | 不做的理由                                                                                          |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 把内联 CSS 改回外链 `<link>`                 | 首访会多一个渲染阻塞往返，当前体量下内联更优；配置里的论证成立                                      |
| 引入 `critical` / `beasties` 做关键 CSS 提取 | 已经全量内联，再做一遍是负收益                                                                      |
| 加 Service Worker 预缓存                     | 静态站 + 边缘缓存已足够；SW 会引入更新失效与调试成本                                                |
| 给所有卡片图 `eager`                         | 首屏之外就该 lazy，纯负收益                                                                         |
| 全站换 AVIF                                  | 240px 尺寸下与 webp 差距 <10%，编码时间与兼容成本上升                                               |
| TOC 改 IntersectionObserver                  | 现有实现"滚到底部也能选中最后一节"更稳；rAF + passive 已经避免了 layout thrashing，收益小于回归风险 |
| 为 Lighthouse 分数加轮播暂停按钮             | 已明确约定，属于"为审计而审计"                                                                      |

## 五、落地顺序建议

1. **P0-1**：加 `s-maxage` + `stale-while-revalidate`，实测 `cf-cache-status` 变 `HIT`。（一次改动，收益最大）
2. **P1-1**：`<Image priority>` + 修正 BaseLayout 注释。（文章页与首页 LCP 同时受益）
3. **P1-2**：CF 后台给 301 加缓存。（部署层，10 分钟）
4. **P2-1**：CSS 按页拆分。（收益中等，需回归）
5. 其余按需。

## 六、可扩展性备注

当文章从 57 篇涨到 300 篇时，会先撞到三处：搜索索引（37KB → 150KB+）、`llms-full.txt`（140KB → 800KB+）、首页卡片 HTML（图片 `srcset` 文本按卡片数线性增长，每张约 130 B）。前两项有缓存可缓解，第三项建议首页限制卡片数并强制分页读取。
